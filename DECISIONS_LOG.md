Every agreed decision goes here as a short bullet. This file is the source of truth — paste it into any new Claude Code sprint or Claude chat before starting work. Nothing here changes without discussing it first.

## Product
- Kitchen compliance enforcement app (UK), not a checklist app
- Tasks require proof (tick/data/photo/note) — can't be faked or skipped
- Critical/high-risk failures require a corrective action before continuing

## Process
- Restarting the build was rejected — reconcile the existing prototype, don't rewrite from scratch
- Every sprint must be committed to git as a save point
- Claude keeps answers short and simple for the user
- Claude pushes back on ideas that don't fit the ICP or app, and suggests improvements

## Standing process rule (effective immediately, all future sprints)
If Claude believes something in an approved plan should change during a build, it must STOP and ask before implementing it — not implement the change and report it afterward, even if the change seems more correct or more consistent with locked architecture. Flag it, wait for a decision, then proceed.
This applies retroactively to nothing already built — Sprint 014's versioning correction (built as an on-the-spot fix to match ARCHITECTURE_LOCK's Versioning Rule, then disclosed) stands as-is and was a reasonable call under the rules in force at the time. This rule governs how deviations from an approved plan are handled from Sprint 015 onward.

## Full product vision (confirmed, expands original scope)
- Three role tiers: top (C-suite, company-wide + stakeholder data), mid (managers/supervisors - assign tasks, manage staff, notified on triggers), base (workers - task execution)
- Task library: grouped by operation segment/role, site-editable, with trigger events (outside min/max), fix instructions, if/then logic
- Each task has a configurable method (e.g. thermometer+photo, filter type choices) and custom fields - not just pass/fail/temperature
- Multiple named instances per equipment type (Fridge 1, Fridge 2, etc.), set up by manager/top tier per venue
- Venue setup wizard: equipment, operational points, staff + roles - guided, intuitive
- Company/branch branding controlled by top tier (colors, logo, contact info)
- Onboarding: manager selects staff, assigns tasks + frequency via tick-box library, can add custom tasks
- End-of-session summary: pass/fail + triggers, sendable to a selected manager
- Trigger notifications: configurable by top/mid tier (push and/or email), top tier can override mid-tier settings
- Shift handover: carry-over notes between shifts
- Multilingual: each staff member selects their own language
- Audit trail: append-only, versioned - nothing overwritten; manager changes to task setup (limits, frequency) create a new version, old version stays visible
- Legal limit checking: task limits checked against a legal-minimum reference table (e.g. fridge/freezer/hot-hold temps); attempts to set outside legal allowance trigger a warning
- Offline: each device queues entries locally with timestamp, syncs when reconnected - no merging/overwrite, all entries additive; manager dashboard shows a "not yet synced" indicator
- Units: support both metric/imperial and Celsius/Fahrenheit
- Inspection data export: management/top tier only

## Notification rules (Sprint 014)

## Multi-site foundation: ShiftHandoverNotes/SessionSummaries/NotificationRules (Sprint 015d) — closes the 015a/b/c/d split
- `ShiftHandoverNotes`/`SessionSummaries` got the standard treatment (required `siteId`, backfilled to the default site, non-nullable domain model) — both describe something that happened at one specific venue.

## Notification firing (Sprint 016) — resumes the sprint paused for the multi-site foundation
- No `Notification`/`TriggerNotification` entity existed before this sprint — Sprint 014 built only `NotificationRule` (the configuration). Confirmed this by reading the schema fresh before planning, not assuming from the task description's framing. Built the full stack from scratch: `TriggerNotifications` table, model, repository (`create`/`watchForUser`/`acknowledge` all built now even though the read/acknowledge sides sit unused until the inbox sprint).
- `TaskSubmissionRepository.submit()` changed from `Future<void>` to `Future<int>` (surfacing the already-computed inserted row id) — needed so a `TriggerNotification` can link back to the submission that caused it. This touched a file outside the originally-approved list; flagged and confirmed before building rather than added unilaterally.
- Matching: active `NotificationRules` where `taskTemplateGroupId` is null or matches the failed task, AND `siteId` is null (org-wide) or matches the submission's site.
- Precedence: matching rules are grouped by their exact `taskTemplateGroupId` (null/"any" is its own group). Within a group, an active top-tier rule suppresses mid-tier rules in that same group — this is the concrete algorithm chosen to implement PROJECT_BIBLE's "top tier can override mid-tier notification settings," confirmed with the user since no exact algorithm was ever specified.
- Fan-out: a rule targeting a specific user creates one `TriggerNotification`; a rule targeting a role tier fans out to every user in that tier — scoped to the submission's site if the rule is site-specific, or across all sites if the rule is org-wide (null `siteId`).
- `notificationRuleId` on `TriggerNotification` references the specific rule *version* active when it fired, not the `ruleGroupId` — preserves exactly what config caused the notification even if the rule is edited later, matching this project's immutable-audit-trail philosophy.
- `channelPush`/`channelEmail` still do nothing — no backend exists. Carrying forward Sprint 014's "configuration intent only" decision unchanged now that real firing exists.
- `TaskController` gained three new constructor dependencies (`NotificationRuleRepository`, `TriggerNotificationRepository`, `UserRepository`) via the same explicit-DI pattern already used throughout — `task_screen.dart`'s `initState` is the only construction site and was updated accordingly.
- Verified with a repository/controller-level test covering: no rules → no notifications; a site-matching rule fires; a rule scoped to a different site does not fire; a top-tier rule suppresses a mid-tier rule in the same trigger scope; PASS submissions never fire anything; specific-person targeting works independently of tier fan-out. All passed. Also ran a real Windows debug build against the existing dev database confirming the schemaVersion 13→14 migration (new table, no backfill needed) executes cleanly.
- No in-app inbox UI yet — deferred to the next sprint (017), per the agreed two-sprint split. Notifications are being created but nothing surfaces them to a manager/top-tier user yet.

## Local data backup/export (Sprint 020) — first feature audit priority
- Raw SQLite file copy, not a structured (JSON/CSV) export — deliberately distinct from PROJECT_BIBLE's separate, later "Inspection data export" item, which serves a different audience (inspectors reading a report) rather than disaster recovery (getting the exact data back onto a replacement device). Confirmed with the user before building, not conflated.
- Implemented via SQLite's `VACUUM INTO ?` (a parameterized `customStatement` on `AppDatabase`) — produces a complete, consistent, compacted snapshot safely while the live connection stays open, avoiding WAL-corruption risk from a naive file copy. Verified with a test that opens the resulting file as an independent sqlite database and confirms it contains real data.

- Dialog logic (`_showBackupDialog`) is duplicated as a private top-level function in both `manager_screen.dart` and `top_screen.dart`, matching this project's established pattern of duplicating small per-screen logic rather than sharing it across ManagerScreen/TopScreen.

## Standing design rule: narrow-width testing (added during the visual/UX pass, Sprint 031)
Every screen touched by any future visual/UX work must be verified at a narrow width (~380px, roughly phone-portrait) in the real Windows smoke test, not just at the wide desktop width the app has always been developed at — resize the running debug build down, don't just eyeball it wide. Applies going forward to any screen-level styling/layout change, not just this sprint.
- Reason: a whole class of real bugs (icon-row overflow, elements clipping/vanishing) was invisible at desktop width and only surfaced once actually resized narrow — this app targets tablets and phones, not just wide desktop, so wide-only testing was never sufficient.
- When reporting verification, name the specific screens tested at narrow width and what was found (clipped/vanished vs. already fine) — not just "verified," so it's clear this was actually checked, not assumed.
- Horizontal scrolling to hide overflow doesn't count as a fix — that just moves the same content off-screen instead of reflowing it.
- **Methodology correction (Sub-sprint 4)**: this dev machine's real Windows DPI scale is 200% (confirmed via `GetDpiForWindow`, not the ~137% figure that appeared in unrelated chat-image-preview scaling notes — a coincidental, unrelated number). A screenshot script that calls `MoveWindow`/`GetWindowRect` without first setting per-monitor DPI awareness on the calling thread (`SetThreadDpiAwarenessContext`) gets inconsistent coordinate interpretation, and a script that resizes to a raw "380" without accounting for this actually produces a window at ~277 *logical* pixels — narrower than the ~380 logical px Flutter itself is laying out against, and narrower than intended. Concretely produced a false positive this sub-sprint: `login_screen.dart`'s staff-tile name appeared to wrap mid-word ("Hughe"/"s") at a raw-380-physical-px capture, but rendered cleanly at the DPI-corrected physical equivalent of 380 logical px (760px on this machine). Going forward, narrow-width verification via screenshot must set thread DPI awareness first and resize to `380 * (GetDpiForWindow / 96)` physical pixels, not a raw 380 — otherwise a genuinely fine screen can read as a false failure (or, in the other direction, a real failure could be missed if the raw value happens to land wide rather than narrow on a different machine's scale factor).

## Exit behaviour + time-windowed tasks (agreed this session)
EXIT BEHAVIOUR:
- Every screen, every tier, must allow log out / get back - never trapped
- Exiting shift activities mid-way is ALLOWED but never silent: leaving before finishing shows a warning ("Some checks aren't complete. This will be recorded. You can return and finish anytime this shift.") and logs incomplete tasks as not-completed (not vanished, stays outstanding). Preserves compliance (nothing silently skipped) without trapping the user.

TIME-WINDOWED TASKS (anti-cheating - stops e.g. closing tasks done at shift start):
- Each task can have a valid time window; outside it the task is visible but locked ("available from 21:00")
- Timestamp of actual completion is always recorded and is what really matters for audit
- HONEST LIMIT: timestamp is device-clock now (fakeable). Time-windows raise the bar against casual cheating but aren't tamper-proof until a backend provides trusted server time (parked backend work).
- DECISION on how windows are defined: BOTH fixed-clock and relative-to-shift, but SEQUENCED. Fixed-clock times NOW (buildable immediately, covers opening/closing case). ## Corrective action redesign (logged ahead of building, real compliance gap found testing the fail flow)

## Due/overdue tracking — Build Order item 5, Sub-sprint A: core (Sprint 031)
Plan proposed and agreed in full before building (frequency scope, overdue-accumulation display, badge treatment, sub-sprint split order — all agreed as recommended). Task referenced "FINALIZED beta build order" — this file has no section under that exact name (same pattern as several earlier references this session that also didn't exist); the real "Build order" and "Exit behaviour + time-windowed tasks" sections it also pointed to do exist and were read in full.
- **Confirmed by reading the actual code before building, not assumed**: `TaskController.loadTasks()` had zero completion-awareness — every active `TaskSchedule` showed in the worker's carousel every single session regardless of whether it had already been submitted for its period. A worker doing their daily fridge check would see it again five minutes after submitting it. This was the real, concrete bug Build Order item 5 exists to close, not a hypothetical.
- **Scope, agreed before building**: due/overdue tracking only applies to the 5 frequencies that describe a pure calendar-time recurrence — `daily`, `twoXDaily`, `threeXDaily`, `weekly`, `monthly`. The other 9 (`perShift`, `perBatch`, `perDelivery`, `perUse`, `perService`, `twoXPerService`, `eventBased`, `asNeeded`, `custom`) stay exactly as they were — always shown, no due/overdue badge — since they're shift- or event-relative concepts this app doesn't model yet (the already-logged relative-to-shift deferral). A disclosed, honest gap, not a silent miscomputation.
- **No schema change** — due/overdue is a pure computation over existing data (`TaskSchedule.frequency`/`.assignedAt` + `TaskSubmission.taskScheduleId`/`.completedAt`/`.status`), not a new stored field.
- New `lib/shared/models/task_schedule.dart` helpers, colocated with `ScheduleFrequency` like `frequencyLabel` already is: `isClockBasedFrequency`, `requiredSubmissionsPerPeriod` (2/3 for 2x/3x-daily, 1 otherwise), `periodStart`/`periodEnd` (weekly starts Monday, UK/ISO convention).
- New `lib/features/tasks/due_status_service.dart` — `DueStatusService.computeStatus(schedule)`: satisfied (current period already has enough PASS/FAIL submissions — skip, don't show) / due (not yet satisfied, still within the period, or a non-clock frequency) / overdue (the immediately-preceding period was also unsatisfied). Deliberately shared (not tucked inside `lib/features/tasks/`'s own controller) since Sub-sprint D's manager-facing overdue notifications will need the identical computation.
- **Overdue accumulation collapses to one flag per schedule, not one entry per missed period** — the check only looks at the single immediately-preceding period, not the schedule's full history. Once any submission satisfies a period, the schedule stops being overdue on the very next check; earlier misses aren't erased, they remain reconstructable from the log's absence of submissions, they just don't keep blocking the active flag or spawn a growing pile of carousel entries. A freshly-assigned schedule (not yet existing through the whole preceding period) is never immediately flagged overdue — checked via `assignedAt` against the previous period's start.
- `TaskSubmissionRepository` gains `countForScheduleInRange` — introduces `selectOnly`+`.count()` for a narrow aggregate query, same rationale as the manager-log-filter work's introduction of `selectOnly`/`distinct` last task: the correct primitive for this specific need, not overbuilding. Only counts PASS/FAIL — deliberately excludes the future `NOT_COMPLETED` status (Sub-sprint B) so an abandoned task doesn't wrongly satisfy its period when the worker returns.
- `ResolvedTask` gains `isOverdue`/`overdueSince`; `StatusBadge` gains a new `StatusKind.overdue` — a distinct icon (`Icons.schedule`, not caution's `error_outline`) so "overdue" doesn't read as the same thing as a caution alert, but reuses the caution colour tokens rather than adding a new one to the deliberately minimal pass/caution/critical palette (agreed as recommended: new *kind*, not a new *colour*). Shown on the task card directly under the title, above the guidance banner, as "Overdue" or "Overdue since [date]".

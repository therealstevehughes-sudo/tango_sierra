## BACKEND - approach decided (researched Aug 2026)
CONTEXT: Steve's partner wants to use the app in his real shops ASAP. That needs the things ONLY a backend provides: trusted (un-fakeable) server timestamps, push notifications, multi-device sync, real auth (not shared-device PINs), cloud storage (data survives lost device). No local shortcut - "give him that much" = building the backend.
DECISION: self-hosted Supabase on Steve's existing IONOS VPS Linux L+ (confirmed: proper Linux VPS, root access, Docker-capable).
WHY Supabase: open-source, bundles Postgres DB + auth (GoTrue) + auto REST API (PostgREST) + realtime sync + storage + edge functions in one Docker stack - matches our exact needs. Self-hosted = full data ownership (good for compliance), predictable cost, no vendor lock-in.
HONEST TRADE-OFFS: self-hosting means WE set up backups, SMTP (auth/push emails), SSL, security (JWT secrets, DB passwords, no example keys), ~1-2h/mo maintenance, 8GB RAM production. Coolify/Dokploy can ease Docker management.
CRITICAL CAUTION: real DevOps, different skill from Flutter. Compliance app + real shop data = security must be right. Steve will set up the server himself with CC's guidance, going slow on security, with a final security review by a backend-experienced person before real shop data goes in.
SCOPE for partner-live (minimum real backend): cloud Postgres (multi-device), real auth, server timestamps, push notifications, cloud storage. NOT IoT/AI/multi-region yet.
Everything was built backend-ready (local drift DB) - so this is migration/integration, not a rebuild.

## Backend Phase 2 - real auth architecture agreed and built (2026-09-01)
DECISION: base/supervisor/venueManager keep the exact same tap-a-name + 4-digit-PIN experience, with the actual check moving server-side. A new Postgres table (`staff_pins`) holds the PIN hash/salt with zero client access at all; a new Edge Function (`pin-login`) is the only way to reach it, verifies the PIN via an atomic Postgres function, and on success mints a real signed Supabase session token. Existing PIN hashes migrate as-is (same hash scheme, no forced resets) - upgrading the hashing algorithm itself is logged as a "harden later" item, not done now, since the plaintext PINs were never stored and can't be re-derived without a reset.
DECISION: Leadership Access (regional/executive) drops the interim PIN entirely for real email + password via Supabase's own auth, rolled out by inviting each person by email so they set their own password (Steve never types a password for them). Two-factor (authenticator app) is an agreed fast-follow after email+password, not bundled into this pass. Leadership sessions persist on the person's own device (normal app behaviour); the shared kitchen tablet still forgets who's logged in on every restart, unchanged.
DECISION: offline login is accepted as a real, known limitation now that PIN-checking is server-side - if the venue's wifi is down, nobody can tap in until it's back. Matches the already-agreed "mostly online" backend scope. Not building a local-fallback login path now; revisit only if the partner's actual shop wifi proves unreliable in practice.
DECISION: PIN lockout is 5 wrong attempts -> 15-minute freeze, enforced entirely server-side (in the database function itself, not the app) specifically because a 4-digit PIN checked over a network is newly guessable (10,000 combinations) in a way the old local-only check never exposed. Verified directly, twice: locked out an account by calling the database function directly, and separately by calling the live function's real internet address directly (bypassing the app entirely) - both times, even the *correct* PIN was rejected while locked, proving the lockout is a hard gate the app can't be bypassed around.
BUILT AND VERIFIED same day: real integration test (not a mock) on the actual Windows build, real network, real server - tap name, correct PIN, real session token comes back; wrong PIN correctly rejected; with the new backend-login switch left off, the existing local-only check keeps working exactly as before, untouched. Full detail, known gaps (SMTP not yet configured for real invite emails, no bulk staff-sync tool yet, no admin UI for linking a new leadership account to their local profile) in `BACKEND_INFRA.md`.

## Standing design rule: narrow-width testing (added during the visual/UX pass, Sprint 031)
Every screen touched by any future visual/UX work must be verified at a narrow width (~380px, roughly phone-portrait) in the real Windows smoke test, not just at the wide desktop width the app has always been developed at — resize the running debug build down, don't just eyeball it wide. Applies going forward to any screen-level styling/layout change, not just this sprint.
- Reason: a whole class of real bugs (icon-row overflow, elements clipping/vanishing) was invisible at desktop width and only surfaced once actually resized narrow — this app targets tablets and phones, not just wide desktop, so wide-only testing was never sufficient.
- When reporting verification, name the specific screens tested at narrow width and what was found (clipped/vanished vs. already fine) — not just "verified," so it's clear this was actually checked, not assumed.
- Horizontal scrolling to hide overflow doesn't count as a fix — that just moves the same content off-screen instead of reflowing it.
- **Methodology correction (Sub-sprint 4)**: this dev machine's real Windows DPI scale is 200% (confirmed via `GetDpiForWindow`, not the ~137% figure that appeared in unrelated chat-image-preview scaling notes — a coincidental, unrelated number). A screenshot script that calls `MoveWindow`/`GetWindowRect` without first setting per-monitor DPI awareness on the calling thread (`SetThreadDpiAwarenessContext`) gets inconsistent coordinate interpretation, and a script that resizes to a raw "380" without accounting for this actually produces a window at ~277 *logical* pixels — narrower than the ~380 logical px Flutter itself is laying out against, and narrower than intended. Concretely produced a false positive this sub-sprint: `login_screen.dart`'s staff-tile name appeared to wrap mid-word ("Hughe"/"s") at a raw-380-physical-px capture, but rendered cleanly at the DPI-corrected physical equivalent of 380 logical px (760px on this machine). Going forward, narrow-width verification via screenshot must set thread DPI awareness first and resize to `380 * (GetDpiForWindow / 96)` physical pixels, not a raw 380 — otherwise a genuinely fine screen can read as a false failure (or, in the other direction, a real failure could be missed if the raw value happens to land wide rather than narrow on a different machine's scale factor).

## Exit behaviour + time-windowed tasks (agreed this session)
EXIT BEHAVIOUR:
- Every screen, every tier, must allow log out / get back - never trapped
- Exiting shift activities mid-way is ALLOWED but never silent: leaving before finishing shows a warning ("Some checks aren't complete. This will be recorded. You can return and finish anytime this shift.") and logs incomplete tasks as not-completed (not vanished, stays outstanding). Preserves compliance (nothing silently skipped) without trapping the user.

TIME-WINDOWED TASKS (anti-cheating - stops e.g. closing tasks done at shift start):
- Each task can have a valid time window; outside it the task is visible but locked ("available from 21:00")
- Timestamp of actual completion is always recorded and is what really matters for audit
- HONEST LIMIT: timestamp is device-clock now (fakeable). Time-windows raise the bar against casual cheating but aren't tamper-proof until a backend provides trusted server time (parked backend work).
- DECISION on how windows are defined: BOTH fixed-clock and relative-to-shift, but SEQUENCED. Fixed-clock times NOW (buildable immediately, covers opening/closing case). Relative-to-shift LATER (needs a real shift-definition system that doesn't exist yet). Task setup supports both so relative is an addition not a rework.

## Corrective action redesign (logged ahead of building, real compliance gap found testing the fail flow)
Two issues found testing the redesigned task carousel's fail flow, logged now — not built yet, this is behaviour change as well as visual, so a proposal is required before building.
1. **`fixInstructions` isn't prominent enough**: on a FAIL requiring corrective action, the fix instructions currently render as plain body text below a `StatusBadge` — informational, not instructional. A stressed worker needs to be told what to do, clearly, not have it read like fine print.
2. **Workers can be blocked from continuing by something they can't do**: `requiresCorrectiveActionOnFail` currently gates SUBMIT behind a single `CheckboxListTile` ("Corrective action completed") that the worker must tick themselves. Many corrective actions aren't things a base-tier worker can actually perform (a Kitchen Porter can't repair a fridge) — forcing them to tick "completed" to proceed either leaves them stuck with no way forward, or trains them to tick it falsely to escape the block. Both outcomes are real compliance risks, not edge cases.
Requested redesign: two recorded paths on a FAIL requiring corrective action, replacing the single checkbox — "I fixed it" (tick + optional description of what was done) and "Reported to manager" (logs it, fires the existing trigger-notification system, lets the worker continue). Neither is a silent skip; both are recorded; the worker is never blocked. Proposal required before building — see the plan that follows this entry once agreed.

## EHO export format (researched) — the decision behind the export's structure (Sprint 031)
This is the specific format decision referenced by name during the EHO/audit export build (see "EHO / audit export" above for the full build writeup) — recorded here as its own entry so the reasoning is findable on its own, not just buried inside the feature's implementation notes.
- **Research basis**: the user researched what UK EHOs actually assess on a visit. Finding: EHOs assess "Confidence in Management" — evidence the system runs daily and problems get caught and corrected — not the sheer volume of paper on file. A dense everything-dump (every individual check, unstructured) is the wrong default format, not merely a suboptimal one: it works against the inspector's actual process, which is built to assess confidence within minutes, not to read a full log line-by-line.
- **Decided structure**: Summary + Exceptions shown by default; the Full Detailed Log exists but is opt-in, gated behind an explicit toggle, **default off**. Summary carries the tally, day-coverage, fail-resolution split, and review/oversight evidence — the things that establish confidence at a glance. Exceptions carries Fails-with-corrective-action, Not-Completed, and Currently Outstanding as distinct subsections, since separating "caught and corrected" from "never reached" from "still open right now" is exactly how an EHO reads a compliance record.
- **Deferred refinement, agreed as deferred rather than built**: the Summary's day-coverage figure ("N of M days in range had at least one recorded check") is an honest activity tally, not a true schedule-vs-actual completion rate (i.e. it doesn't check whether *every* scheduled task on an active day was actually completed, only that *something* was). Building the true rate needs the day-by-day scheduled-vs-submitted comparison that Sub-sprint A/C's due/overdue machinery could support, but wasn't in scope for this pass — logged as a named follow-up, not silently left out.

Both more readable for an inspector and directly shrinks the exact table that was hitting the pagination bug; kept even though the pagination bug is now also fixed separately, since it's a genuine quality improvement independent of it.
